# Довести до работающего URL

## Аккаунты и ручные действия

Сначала заверши всё, что можно без облака: код, ассеты, rules, локальные проверки, workflows, `.env.example`, скрипт проверки конфигурации. Затем настрой реальный проект. Если вход уже есть, не проси входить заново. Открой нужную страницу инструментом браузера; при sign-in остановись для пароля/2FA и продолжай после подтверждения входа. Не пытайся обходить CAPTCHA. При отсутствии доступа к браузеру укажи точную страницу и ровно нужные поля.

Не проси владельца изучать Firebase или самостоятельно придумывать конфигурацию. Агент должен сам получить web app config из выбранного проекта после входа, проверить его полноту и внести публичные параметры в нужное место. При UI-only настройке использовать доступные инструменты честно; при CLI пользоваться официальными командами, не угадывать синтаксис.

## Firebase

Создай отдельный проект с понятным именем, если подходящего ещё нет; существующий используй только при однозначной связи с этой игрой. Оставь бесплатный тариф. Зарегистрируй web app. Настрой email/password Auth и Realtime Database с выбранным доступным регионом, затем сразу закрой доступ проверенными production Rules, не оставляй test mode. Настрой разрешённый Pages-домен для Auth и локальный dev-домен при необходимости. Проверь password reset flow и реальные ограничения/квоты почтовых писем без обещаний неограниченной отправки.

Параметры в `.env.example`: `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_DATABASE_URL`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`. Добавляй только реально используемые остальные поля. Для локальной разработки отдельно флаг emulator; запрещено автоматически подключать production DB из emulator-тестов. Vite config не содержит приватных credential-полей.

Production database rules публикуются воспроизводимой командой, а не только ручным копированием. Первая публикация может выполняться авторизованным CLI владельца. Для автоматического deploy Rules из Actions по возможности настрой GitHub OIDC / Workload Identity Federation с минимальными правами, если это возможно без оплаты; проверь условия сервиса. Если это недоступно, обеспечь явно документированный ручной `deploy:rules`, отдельный статус и не называй эту часть автоматизированной. Не создавай долгоживущий приватный JSON-ключ без необходимости и не проси прислать его в чат. Не используй deprecated login tokens как неявный обязательный путь. Обновление frontend не требует cloud admin secrets.

## GitHub

Выбери существующий целевой repository или создай отдельный `hidden-pictures` при доступном аккаунте. Для бесплатной Pages-публикации сначала проверь текущие условия тарифа/видимости. Новый репозиторий может быть public: код и карточки публичны, комнаты приватны через Rules; объясни это в отчёте. Не делай существующий private репозиторий public без отдельного указания. Если доступная учётная запись не позволяет Pages в private repo, назови конкретный выбор/ограничение, не обходи его.

Настрой Pages source = GitHub Actions. Для frontend config используй repository variables или один явно публичный конфигурационный файл — эти поля не серверные секреты. Проверка обязательных значений должна останавливать production build/deploy при отсутствии параметров, а не выкатывать сломанную страницу. Локальная сборка для эмуляторов имеет отдельный предсказуемый путь.

## CI/CD

Создай рабочие workflows с актуальными совместимыми версиями actions, проверенными по официальным источникам. Минимальные permissions; зависимости закреплены lockfile.

- Pull request: install, typecheck, lint, unit, asset validation, emulator rules tests, критический E2E и build. Без production-секретов и деплоя, без `pull_request_target` с недоверенным кодом.
- Push в фактическую default branch: те же необходимые проверки, затем production build и upload-pages-artifact / deploy-pages. Настоящий base path репозитория; `.nojekyll` если требуется выбранным способом. Одновременные deployment ограничены concurrency.
- `workflow_dispatch`: повторный ручной запуск.
- Browser failures: сохранить trace/screenshot как краткоживущий CI artifact без credential-данных. Не загружать реальные профили браузера.
- При изменении Rules не выкатывать frontend с ожиданием ещё не опубликованной несовместимой схемы; предусмотреть порядок миграции и явную проверку readiness.

Pages hash routing предпочтителен: прямой reload приглашения `/#/room/...` работает без backend rewrite. Ссылки на карты и manifest учитывают `import.meta.env.BASE_URL`. Не предполагать, что сайт расположен в корне домена.

После push дождись результата Actions, исправь реальную ошибку workflow при необходимости и открой опубликованный адрес. Нужен online smoke test с отдельными клиентами. Не принимать успешный workflow за доказательство того, что регистрация и комнаты работают. Если среды не дают проверить production полностью, перечисли конкретно непроверенные действия.
