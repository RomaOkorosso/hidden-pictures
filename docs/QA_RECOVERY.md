# Локальная QA-среда, восстановление и обновление

QA не использует `.env.local`, облачные аккаунты, Firebase CLI login или Supabase. Все данные синтетические. Проект `demo-hidden-pictures`; браузер использует namespace `demo-hidden-pictures-default-rtdb`, куда CLI загружает правила. Тесты Rules загружают те же правила в отдельный namespace `demo-hidden-pictures` на том же изолированном эмуляторе.

## Воспроизведение

1. Выбрать Node из `.nvmrc` (Node 24 LTS, не системный Node 18), установить JDK 21+.
2. `npm ci`.
3. `npx playwright install chromium` (в Linux CI: `npx playwright install --with-deps chromium`).
4. `npm run typecheck`, `npm run lint`, `npm run build`.
5. `npm run qa` — сам запускает Auth/RTDB и Vite, выполняет unit/assets/rules и браузерные сценарии, останавливает сервисы.

Отдельно: `npm test` — unit/assets; `npm run test:rules` и `npm run test:e2e` — каждый поднимает собственную среду. Не запускать эти три обёртки одновременно. Нужны свободные loopback-порты 19000, 19099, 14400, 14401, 14402 (резерв) и 4177. При конфликте запуск прекращается, чужие процессы не останавливаются. Playwright не подключается к уже работающему Vite.

Первый запуск Firebase CLI скачивает Java-эмулятор; установка Playwright скачивает Chromium. Далее игровые запросы идут только в локальные сервисы. Для браузеров в тестах дополнительно запрещены HTTP-запросы на внешние домены.

## Доказательства

- `.qa/playwright-results.json` — машинный итог.
- `playwright-report/index.html` — отчёт (`npx playwright show-report`).
- `test-results/**/player-*-trace.zip` — отдельная трасса каждого игрока (`npx playwright show-trace <path>`).
- `test-results/**/{captain-key,guesser-board,agent-victory,mobile-finished}.png` — реальные скриншоты.
- `docs/qa-evidence/` — компактные сохранённые результаты итоговой проверки.

Трассы и временные артефакты игнорируются git; они содержат только локальные синтетические сессии. При новом запуске Playwright перезаписывает `test-results`.

## Сбой и восстановление

Обычный выход из `emulators:exec`, в том числе провал теста, останавливает эмуляторы. При аварийном завершении проверить PID и командную строку процесса, занятого на QA-порте, и остановить только оставшийся процесс этого запуска. Не применять `killall java/node`, не удалять пользовательские Firebase configstore или `.env.local`.

Временную папку `.qa` можно удалить после остановки сервисов. Следующий запуск создаст конфигурацию снова. Никакие реальные комнаты и аккаунты не требуется очищать. Не импортировать production-экспорты в QA.

Для сравнения со старой версией создать отдельный detached worktree от базового коммита из `QA_REPORT.md`; текущие исправления и доказательства сначала сохранить. После изменения зависимостей выполнить `npm ci`, затем полный `npm run qa`. После изменения генератора выполнить `npm run rules:generate` и повторить Rules + E2E. Генератор и `database.rules.json` должны изменяться вместе.

## Выпуск и откат

Эта работа не публикуется автоматически агентом. Нужны отдельное разрешение владельца и выбранная среда. GitHub workflow на основной ветке публикует Pages, поэтому даже push/merge в неё является публикацией.

После разрешения сначала проверить совместимость и опубликовать проверенные Rules в выбранном проекте, затем frontend; существующие комнаты не удалять. Облачные данные не являются частью локального отката. При откате frontend сохранять исправленные запреты доступа: старые permissive Rules возвращать нельзя. Перед любым будущим production smoke использовать специально созданные тестовые комнаты и отдельное разрешение, не реальные комнаты пользователей.
