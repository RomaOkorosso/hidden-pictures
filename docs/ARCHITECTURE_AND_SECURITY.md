# Архитектура, конкурентность и секреты

## Граница инфраструктуры

GitHub Actions выполняет проверки, сборку и доставку. Pages отдаёт статические HTML/JS/CSS/WebP. Firebase Auth хранит учётные записи; Realtime Database хранит комнаты, события и приватные ключи, доставляет realtime-обновления, контролирует доступ серверными Rules. Постоянный Node/Python/VPS/WebSocket-сервер не требуется. Это проект для доверенных друзей без рейтингов и денег, но угадывающий не должен читать ответы через DevTools или поддельный запрос.

Проверь актуальные бесплатные лимиты и доступность сервисов по официальным источникам до provisioning. Не обещай безлимитность и не включай платный тариф. Firebase Cloud Functions не должны быть обязательны. Нельзя использовать Admin SDK в браузере.

## Структура кода

Раздели чистую доменную модель игры, адаптер Firebase, UI и ассеты. Компонент React не должен напрямую произвольно переписывать дерево комнаты. Команды домена типизированы, состояние версионировано, timestamps серверные там, где это влияет на доступ и присутствие. Все подписки очищаются при выходе/смене комнаты. Игровой рендер не создаёт повторно сетевые подключения.

Локальная демонстрация/тестовый адаптер может работать без облачного проекта, но должен быть явно обозначен и не подменять настоящий online mode. Production без необходимой конфигурации выдаёт понятное состояние и не симулирует онлайн-комнату в localStorage. Локально предпочтительны Firebase Auth/Database emulators, а не самописная имитация Firebase.

## Данные и права

Спроектируй разделённые публичные для участников и секретные узлы. Не выдавай чтение родительского узла, включающего секрет: разрешения RTDB наследуются, Rules не фильтруют прочитанные поля.

Публичное состояние игры: ID партии, состав с публичными именами и ролями, порядок ID карт, активная команда, фаза, подсказка, открытые результаты, оставшиеся попытки, результат, версия. Приватный ключ: соответствие позиции роли, доступ только двум фиксированным UID капитанов этой партии; после завершения допустима выдача ключа её участникам. Пользователь не может сам изменить UID/роль и получить секрет. Нельзя читать список всех комнат, аккаунтов или чужие профили с email.

В лобби разрешён вход авторизованного пользователя по приглашению с жёсткой проверкой статуса, лимита игроков и собственной UID. Запрети изменение чужих записей и удаление чужой комнаты. Публичный индекс кода комнаты должен содержать только необходимый ID и не раскрывать секреты; перечисление индекса запрещено. Если индекс не нужен, лучше прямой room ID, дополненный атомарно резервируемым коротким кодом.

## Доверие при раздаче без функций

Клиент капитана может создавать секретный ключ: капитан по правилам имеет право его знать. Владелец-угадывающий не должен инициировать раздачу через процесс, в котором он получает ключ. Старт из UI владельца может запросить инициализацию от назначенного капитана; показать «ожидаем капитана» при отсутствии его соединения. Выбери один детерминированный инициализатор и обработай повторную доставку запроса. После фиксации ключ неизменяем, сменить его под предлогом reconnect нельзя. Серверные Rules должны проверять набор значений, количество ролей и соответствие ровно 20 позициям, используя проверяемую структуру/сгенерированные развёрнутые условия, если язык Rules ограничен. Проверка только в TS недостаточна.

Явно опиши эту модель доверия в README: капитаны уже знают ответы, случайность и честность раздачи не являются криптографически доказанными. Это не разрешение давать угадывающему ключ и не повод отключать контроль правильности открытий.

## Авторитетность правил и атомарность

Правила сервера обязаны проверять допустимость каждого изменения и правильность результата открытия относительно приватного ключа. Угадывающий не может объявить убийцу своей карточкой, увеличить число попыток, переключить ход произвольно, отредактировать старую подсказку, счёт, ключ или историю. Реализуй минимально необходимые записи; для маленького фиксированного поля можно генерировать Rules из читаемого исходника. Сгенерированные Rules включи в репозиторий, их соответствие генератору проверяй в CI.

Выбери атомарный протокол команд/переходов, совместимый с тем, что угадывающий не имеет чтения секретного родителя. Не делай transaction над общим предком public+secret, чтобы затем расширить `.read` ради работоспособности. Публичная транзакция с проверкой закрытого ключа серверными Rules возможна; любые связанные записи должны фиксироваться согласованно, либо выводиться из одного источника истины.

Ожидаемая версия состояния, match ID, turn ID и уникальный action ID защищают от повтора, гонок и устаревших запросов. При двух одновременных открытиях, особенно убийцы/нейтрали и своей карты, разрешён только один последовательный допустимый порядок. Запрос, начатый в старом ходе, не становится действием нового хода после автоматического retry. Повторный tap и повтор после reconnect не расходуют попытки дважды. Отдельный блокирующий UI не заменяет транзакцию.

Счёт и победитель вычисляются из принятого публичного состояния и проверяются сервером. Логи не должны содержать будущие ответы или скрытый seed. Не раскрывай map через error payload, URL, localStorage, analytics, отладочные глобальные объекты или sourcemap fixtures в production. Капитанский экран не должен на миг отрисовываться до загрузки подтверждённой роли.

## Reconnect, retention, эксплуатация

Присутствие через `.info/connected`, server timestamps и `onDisconnect`, учитывая несколько вкладок одного UID. Не доверять локальным часам для захвата владельца. Перезагрузка восстанавливает auth и состояние из облака. Текущая подсказка, ход, открытые карты и результат переживают закрытие вкладки хоста.

Не подписывайся на корень базы. Ограничь размер подсказки, имён, количества игроков/событий, частоту повторных команд там, где Rules позволяют. Сохраняй только ограниченное число недавних партий комнаты; реализуй ограниченную по объёму безопасную уборку просроченных данных при допустимых пользовательских операциях. Не обещай автоматическое удаление по wall-clock без реально настроенного исполнителя. Документируй срок хранения и способ ручной уборки, если scheduler не подключён. Не добавляй платный scheduler ради уборки.

## Обязательное доказательство защиты

Rules tests выполняются через клиентские credentials с разными UID, не через обход правил Admin SDK. Admin допустим только для подготовки fixtures эмулятора. Тестировать прямое чтение key path и родителя, запись в роли, подделку reveal, фазу, version, turn, clue, result, откат завершённой партии, попытку входа в активную/полную комнату. Не ограничиваться тем, что UI прячет кнопки.
