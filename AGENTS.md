# Правила исполнения

Цель: рабочая онлайн-игра с картинками, регистрацией, комнатами и двумя капитанами. Никаких фиктивных кнопок, незавершённых экранов, заглушек вместо сетевого режима или обещаний «дописать позже».

## Приоритеты

Указания пользователя → сохранность существующего проекта → эти документы → техническое решение исполнителя. Для обратимых решений не нужен отдельный вопрос. Архитектурные решения документируй, но не жди их утверждения.

Стек по умолчанию: TypeScript strict, React, Vite, Firebase Authentication (email/password), Firebase Realtime Database, Vitest, Testing Library, Playwright, Firebase Emulator Suite. Используй совместимые актуальные стабильные версии, lockfile и поддерживаемый Node LTS; версии проверь по официальной документации. Не меняй стек просто ради предпочтения. Если репозиторий уже содержит пригодную реализацию, доработай её, сохранив требования.

## Ограничения

- Actions используется для CI/CD. Не запускай в runner постоянный игровой сервер, бесконечные keep-alive, туннели или cron вместо realtime.
- Сайт статический на Pages, синхронизация и аккаунты в Firebase. Облачные функции и платный тариф не требуются базовой архитектуре.
- Не подключай оплату. Если текущие условия бесплатного сервиса несовместимы, сначала проверь бесплатную альтернативу и зафиксируй конкретный блокер; не скрывай стоимость.
- Не добавляй аналитику, рекламу, чат, платёжную систему, AI-генерацию или публичный матчмейкинг.
- Не выдавай frontend-проверки за серверную защиту. Обязательны отрицательные тесты правил доступа через обычный клиентский SDK.
- Firebase web config публичен по назначению. Секретные service account keys, токены CLI и пароли никогда не входят в Vite env, git, сборку и логи.
- Не отключай проверки/правила безопасности ради прохождения тестов.
- Не отправляй наружу персональные данные. Тесты используют синтетические аккаунты и отдельные тестовые комнаты.

## Процесс

Сначала изучи файлы, затем измени. Декомпозируй на проверяемые шаги. Исполняй команды сам. Добавляй тесты для правил игры, конкурентного доступа, приватности и критических пользовательских сценариев; не трать время на тесты тривиальных декоративных компонентов. Для визуальной проверки используй реальные браузерные скриншоты внутри рабочей среды и проверяй результат. Если инструментов не хватает, установи разрешённые зависимости или честно отметь непроверенное.

Сохрани команды `npm ci`, `npm run dev`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run test:rules`, `npm run test:e2e` (или документированные эквиваленты при уже существующем другом менеджере). E2E должен самостоятельно поднимать приложение и эмуляторы либо иметь одну явную обёртку, делающую это. Никаких скрытых предварительных ручных запусков.

Не коммить `node_modules`, `dist`, credential-файлы, `.env.local`, дампы реальных комнат. Внешние операции выполняй только для однозначно выбранного проекта. Не меняй глобальные настройки пользователя. При завершении сохрани `README.md`, `.env.example`, `docs/PROGRESS.md`, `docs/DELIVERY_REPORT.md`, инструкции восстановления и обновления.
